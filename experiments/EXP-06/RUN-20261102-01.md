## Confounders / limitations

- n = 1 per arm. Same model family for all workers. The test failure message plus the test name ("validator accepts", years 0099) nearly names the cause, so the task was too easy to discriminate.
- **The original P1 D2 was missed by the builder** but was not a failing test at the time: the reviewer found it by reading the code. This run starts from a failing regression test, which is a much easier signal. A discriminating repeat would plant the defect **without** a failing test and ask a worker to implement or review the date code.
- The control instruction "do not use memory" is weak: the repeat worker did not see or use memory either, so both arms are effectively "no memory".
- Case 1 deleted the comment naming `Date.UTC` in `calendar.test.ts`. Case 2's test name and the original code's `Date.UTC(2000, …)` + `setUTCFullYear` pattern (visible in `git show HEAD`) were clues. Both case 2 workers named the regressing commit 92cfc89 in their reports.

## Findings for the evaluation

1. **Memory retrieval by workers is opt-in and was not exercised (0 of 3 calls).** Project memory reaches coordinators and branches passively through the index, but built-in `worker` subagents get only the `memory` tool. A correction rule stored as memory therefore does not influence the agents that write most code unless the coordinator restates it in the brief, or the agent definition tells workers to consult memory. Changing agent definitions was out of scope here.
2. The memory write path works as designed: proposed by the branch, applied by the root with `remember`, visible in the index for branches within about a minute.
3. Self-improvement scoring: the evidence supports "can record a scoped, evidenced rule". It does not support "the rule changes later agent behaviour".
